## Two trust zones

### Zone A — external and untrusted

This includes every HTTP request, especially Telegram webhook payloads, message content, network authentication headers, user-provided data, issue and pull-request content, and any input crossing a network. A sender may be mistaken, spoofed, or malicious.

Data from this zone must be validated at the boundary, receive size and scope limits when a new route appears, and never become a query, command, outbound URL, or HTML content without controls.

### Zone B — operator-controlled runtime

This includes reviewed code, the API process, environment configuration, connector ports, containers, `TELEGRAM_BOT_TOKEN`, `OPERATOR_API_TOKEN`, and `TELEGRAM_WEBHOOK_SECRET`. It is trusted only to the degree that the operator controls the host. It does not make a leaked environment variable safe or provider data trustworthy.

The principal boundaries are HTTP input into the API, environment configuration at startup, and hub commands leaving for a connector or provider. Each crossing needs validation, least privilege, and logs without secrets.

## Assets to protect

- Integrity of source code, dependencies, CI, and container artifacts.
- Availability of the local API and future connector actions.
- Provider secrets, tokens, cookies, and operating configuration, which must not appear in the repository, fixtures, or logs.
- Conversation data, contact identifiers, and logs. They are not persisted in 1a, but become sensitive data once persistence exists.

## Assumptions and limits

- An operator workstation, GitHub account, or Docker daemon can be compromised; the repository cannot protect itself when the root trust platform is lost.
- Contributions and issues from strangers are untrusted content. Do not run commands suggested in them before reading them.
- Green CI proves only the commands that ran; it does not prove an Internet-facing deployment is safe.
- `OPERATOR_API_TOKEN` does not make the API a user or RBAC system. It is only the temporary local operator key for 1a.
- No persistence means no durable history, but it also means no deduplication or recovery after the process dies.
- `npm run check` passed with seven test files, fifty tests, and a build; `npm audit --audit-level=low` reported zero vulnerabilities; Compose configuration, non-root/read-only runtime behavior, an independent audit, GitHub CI, and CodeQL also passed for the Phase 1a candidate at `7141949`.
- There has been no real token or network test. Do not infer Telegram compatibility from mocks or internal HTTP tests.
